How to read this (a thirty-minute path)

Thirty minutes is enough: see the live demo first, then read the contract, the guard, the pull requests, and the process behind them, in that order.

  1. fhir.mvcprogrammer.com (5 min). Press Search, pick a patient, then create one of your own in the edit panel and patch, replace, and delete it. The "Under the hood" log shows every request the browser made and every call the function made to the FHIR sandbox.
  2. api/openapi.yaml (5 min). The contract was written and committed before the code, for the reads and again for the writes. Every status code an operation can return is declared; errors are RFC 9457 problem details.
  3. PatientWriteService.cs (5 min). The guard that keeps the seeded patient read-only, ties every created patient to the visitor's session, and makes creates idempotent through a FHIR conditional create. Nothing is kept in the function.
  4. PR #152 and PR #159 (10 min). One feature PR and one fix PR, each with the design choice, the alternative weighed, and the verification in the description. Both were pair-programmed with an AI assistant under written working rules and reviewed by hand before merge; 202 tests cover the FHIR function.
  5. The project board and docs/BURNDOWN.md (5 min). Every change starts as an issue, is groomed with an estimate before it is Ready, and lands through a reviewed pull request. The definitions of Ready and Done are written down.

The repository is public: github.com/mvcprogrammer/mvcprogrammer.com, 355 commits since 2026-10-06, 113 pull requests. The grades below are mine; the links let you check them.

The HL7 ETL demo (an eight-minute outline)

HL7 v2 messages land in Postgres integration tables, a .NET loader maps them to FHIR R4 and bulk-loads the public sandbox, and the explorer reads the result back. Eight minutes, a handful of terminal commands, one browser tab, synthetic data only. The full runbook with every command is docs/HL7-ETL-DEMO.pdf.

  1. Frame it (30 s). A workload every health system runs, built end to end on an Angular/C# .NET stack in one sprint: api/src/Hl7.Etl.
  2. Show the landing tables (1 min). status, then the message counts by type and one raw ORU message: MSH, PID with the MRN, OBR, and OBX lines with LOINC codes and UCUM units. Every message is a row, unique on its control id, so a redelivery lands once: Sql/001_landing.sql.
  3. Show that landing is idempotent (30 s). generate again: 0 landed, 67 had already landed.
  4. Replay the load (2 min). requeue, then load: each batch of up to 25 messages becomes one transaction bundle, every entry a conditional create, and the summary reads 0 resources created, 268 already present. The property a real engine needs after a crash or a redelivery: Services/LoadService.cs.
  5. Read it back (2 min). In the explorer, family name blank and https://mvcprogrammer.com/fhir/etl| in the Identifier field lists the cohort; pick a patient and show the encounter and the vital signs. The explorer did not change for this.
  6. Code tour (2 min). The schema, AdmissionMapper.cs or ResultMapper.cs, the loader, and PR #223: the public server refused conditional references and a failed batch was being re-claimed in the same run, both found by running it for real and fixed with tests the same afternoon.
  7. Close (30 s). The production version of this shape is the most recent position on the resume, on SQL Server at enterprise scale; here it is Postgres, a public sandbox, and a public repository with epic #216: four slices, four reviewed pull requests, 43 tests.

Five case studies

A problem, a decision, and where to see it. The bold text is the short version.

1. The FHIR explorer epic

Spec first, guard on the server, faults found by probing the live host. Visitors can create, change, and delete demo patients on a shared healthcare sandbox and can touch nothing else.

  • Decisions before code. Verbs, guard, budget, and idempotency were settled and written on epic #125 before the first slice.
  • Contract first. The OpenAPI document changed first; the function answered 501 until the handlers existed.
  • The guard holds no state. The seeded patient is read-only; every created patient carries the visitor's session token as a FHIR identifier; anything else answers 404, so nothing can be probed. PatientWriteService.cs
  • The sandbox enforces idempotency. A create is a FHIR conditional create keyed on the Idempotency-Key header; a retry returns the same patient with 200.
  • Three edge faults, one afternoon, each with its cause written down. Cloned CloudFront behaviors allowed only the read methods; a signed request to a Lambda function URL needs the body's SHA-256 in a header; the single-page-app's 403-to-index mapping swallowed the API's own 403. All three are now runbook rules. PR #159

2. AI-assisted engineering, as practiced here

The assistant works under written rules, its output passes the same gate as any other change, and the engineer owns every decision.

  • The rules are written down. Before anything outside the repository's established patterns, the assistant searches public solutions first, compares at least two approaches with their trade-offs, states the choice, and stops to ask when the comparison is not clear. The coding standard it works from is addressed to engineers first and assistants second.
  • A rule in action. The JSON Patch applier for patient edits: a general package weighed against an eighty-line applier over five fields, the small one chosen, the reasoning in PR #152.
  • Same gate for everyone. AI-written or not, a change needs an issue, a branch, a passing CI run of nine suites, dotnet format, and a reviewed pull request; the branch rulesets do not know who typed it.
  • Velocity with a record. The writes epic, six slices and two fixes, shipped in two days; every slice has its PR with the decision and the verification, so the speed can be audited after the fact. Epic #125
  • Responsible use is a boundary, not a slogan. Synthetic data only, no secrets in the repository or in a prompt. The same boundary would apply to PHI: nothing identifiable reaches a model.
  • Where an AI feature would go first. A plain-language visit summary over a demo patient's conditions and vitals, generated server-side from synthetic data, with the prompt and the model version logged and the output labelled as generated. Small, bounded, and reviewable, which is how the first one should be.

3. One site, four stacks: keeping delivery targets in step

One content change, four stacks, one commit. The same site ships in vanilla JavaScript, Blazor WebAssembly, Angular, and React from one bucket behind four distributions, which is the discipline a web, desktop, and mobile portfolio needs.

  • The rule is written down. A content, markup, or behavior change goes to all four editions in the same commit; each edition's colophon describes its own stack.
  • The rule under load. The explorer left all four editions in one change, 119 files removed and 48 changed, and the four test suites stayed green. PR #148
  • The payoff. The explorer itself was then built once, as its own Angular app at fhir.mvcprogrammer.com, rather than four times.
  • The bridge to mobile. The Blazor edition's components are the ones a .NET MAUI Blazor Hybrid shell hosts, so the first mobile build would start from code that already exists and has 124 tests.

4. The engineering process

Issue before code, groomed before Ready, reviewed before merge, standard enforced by the build.

  • Every change starts as an issue on the public board and lands through a pull request that CI must pass.
  • Ready means groomed. Scope, acceptance criteria, priority, size, a Fibonacci estimate, and a sprint decision; the definitions of Ready and Done are in docs/BURNDOWN.md.
  • The build enforces the standard. The root .editorconfig names the rule behind each setting, violations fail dotnet build, and dotnet format runs on every PR.
  • Security is in the pipeline, not a checklist. Strict CSP with no inline code, Origin Access Control on every origin, OIDC deploys with no stored keys, SHA-pinned actions, branch rulesets, secrets outside the repository. docs/DEPLOY.md

5. HL7 v2 to FHIR, end to end

A workload every health system runs, built end to end on an Angular/C# .NET stack in one sprint: messages land in integration tables, an ETL maps them to FHIR R4 and bulk-loads the server, the explorer shows what landed. Synthetic data only; the production version of the same shape is the most recent position on the resume.

  • Landing tables first. ADT^A01 admissions and ORU^R01 results land as rows in a Postgres hl7.messages table, unique on the message control id so a redelivery lands once. The application calls only functions: claim a batch in arrival order with FOR UPDATE SKIP LOCKED, complete, fail, requeue. The landing table is the only record of progress.
  • Parse at the boundary. AdmissionMapper and ResultMapper read PID, PV1, OBR, and OBX through an MIT-licensed v2 parser and build Patient, Encounter, and Observation with the Firely SDK: LOINC codes, UCUM units, v3 ActCode classes, identifiers typed MR and VN. A message that cannot be mapped names its control id, the field, and the reason, and the batch goes on without it.
  • Bulk-load idempotently. The loader posts one transaction bundle per batch, every entry a conditional create keyed on the ETL identifier, through a resilient HttpClient with timeouts and retries. Replay the whole feed and the server reports every resource already present, nothing created.
  • What the live server taught. The public sandbox refuses conditional references inside a bundle, so references within a batch become in-bundle urn:uuid references and references across batches are resolved by one identifier lookup; a failed batch keeps its claim so a run cannot spin on it. Both are in the tests and the pull request that found them.
  • Read it back. Every resource carries the identifier system https://mvcprogrammer.com/fhir/etl, so the cohort is one search away in the explorer: put https://mvcprogrammer.com/fhir/etl| in the Identifier field with the family name cleared.

Why this matters for clinical and operational tools

FHIR R4 is how clinical data leaves certified EHRs, and a tool that reaches the floor of a facility has to be right about the boundary around that data before it is right about anything else.

  • Real R4, not a mock. The function parses live bundles from a public HAPI server with the Firely SDK, follows paging links, and maps only the US Core fields the page needs. Patient, Condition, Encounter, and Observation are the same resources clinical and operational tools consume.
  • The trace is an observability habit. Every upstream call is reported with its status, timing, and page count, so a silent EHR or integration failure has nowhere to hide. Application Insights is the Azure home for the same instinct.
  • The PHI boundary is designed in. Synthetic data only, nothing stored, request metadata the only thing logged, a guard that keeps one visitor from another's records, and a strict CSP in front of it all.
  • Where it would go next. Encounter and Observation views on a phone or tablet through a MAUI Blazor Hybrid shell over the existing components, then the bounded AI summary above, each behind the same guard.
