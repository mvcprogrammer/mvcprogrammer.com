How to read this (a thirty-minute path)

Thirty minutes is enough: see the live demo first, then read the contract, the guard, the tests, and the process behind them, in that order.

  1. fhir.mvcprogrammer.com (5 min). Press Search, pick a patient, then create one of your own in the edit panel and patch, replace, and delete it. The "Under the hood" log shows every request the browser made and every call the function made to the sandbox.
  2. api/openapi.yaml (5 min). The contract was written and committed before the code, for the reads in October and again for the writes. Every status code an operation can return is declared; errors are RFC 9457 problem details.
  3. PatientWriteService.cs (5 min). The guard that keeps the seeded patient read-only, ties every created patient to the visitor's session, and makes creates idempotent through a FHIR conditional create. Nothing is kept in the function.
  4. PR #152 and PR #159 (10 min). One feature PR and one fix PR, each with the design choice, the alternative weighed, and the verification in the description. 124 tests cover the FHIR function.
  5. The project board and docs/BURNDOWN.md (5 min). Every change starts as an issue, is groomed with an estimate before it is Ready, and lands through a reviewed pull request. The definitions of Ready and Done are written down.

The repository is public: github.com/mvcprogrammer/mvcprogrammer.com, 278 commits since 2026-10-06, 162 pull requests. The grades below are mine; the links let you check them.

Three case studies

Each one is a problem, the decision taken, and where to see it. Together they cover the JD's three themes: hands-on design, engineering practice, and judgment under constraints.

1. The FHIR explorer epic: spec first, guard server-side, faults found live

The problem was adding create, replace, patch, and delete to a public demo over a shared healthcare sandbox without letting a visitor touch anything but their own records. The decisions, recorded on epic #125 before any code: the OpenAPI contract changed first and the function answered 501 until the handlers existed; the guard lives in the function, not the browser (the seeded patient is read-only, every created patient carries the visitor's session token as a FHIR identifier, anything else answers 404 so nothing can be probed); creates are idempotent through a FHIR conditional create keyed on an Idempotency-Key header, so the sandbox enforces it and the function keeps no state; writes have their own rate budget. A general JSON Patch library was weighed against an eighty-line applier over five scalar fields and set aside, with the reasoning in PR #152.

Going live surfaced three edge faults in one afternoon, each diagnosed with curl and fixed with a one-line cause written down: cloned CloudFront behaviors allowed only the read methods; a signed request to a Lambda function URL needs the body's SHA-256 in a header; and the single-page-app's 403-to-index mapping swallowed the API's own 403, replaced by a viewer-request function (PR #159). All three are now rules in the runbook.

2. The four-editions mirror rule: one content change, four stacks, one commit

The site ships as vanilla JavaScript, Blazor WebAssembly, Angular, and React, served from one bucket behind four distributions, with the same stylesheet and the same content. The rule is written into the repository's instructions: a content, markup, or behavior change goes to all four in the same commit, and each edition's own colophon describes its own stack. PR #148 is the rule under load: the explorer left all four editions in one change (119 files removed, 48 changed), the kiosk-only dialog became a reusable demo dialog in each stack, and the four test suites stayed green. The payoff shows in the opposite direction too: the explorer itself was then built once, as its own Angular app, rather than four times.

3. The engineering process: issue before code, groomed before Ready, reviewed before merge

Every change in the repository starts as an issue on the public board, moves Backlog to Ready only with scope, acceptance criteria, priority, size, a Fibonacci estimate, and a sprint decision, and lands through a pull request that CI must pass; the definitions of Ready and Done are in docs/BURNDOWN.md. The coding standard is enforced by the build where a tool can enforce it: the root .editorconfig names the rule each setting implements, EnforceCodeStyleInBuild turns violations into build errors, and dotnet format runs on every PR. The standard also sets working rules for AI assistants (search public solutions before designing from scratch, compare two approaches, state the choice), which is how the JSON Patch decision above was made.
