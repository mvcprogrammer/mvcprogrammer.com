How to read this (a thirty-minute path)

Thirty minutes is enough: see the live demo first, then read the contract, the guard, the tests, and the process behind them, in that order.

  1. fhir.mvcprogrammer.com (5 min). Press Search, pick a patient, then create one of your own in the edit panel and patch, replace, and delete it. The "Under the hood" log shows every request the browser made and every call the function made to the sandbox.
  2. api/openapi.yaml (5 min). The contract was written and committed before the code, for the reads in October and again for the writes. Every status code an operation can return is declared; errors are RFC 9457 problem details.
  3. PatientWriteService.cs (5 min). The guard that keeps the seeded patient read-only, ties every created patient to the visitor's session, and makes creates idempotent through a FHIR conditional create. Nothing is kept in the function.
  4. PR #152 and PR #159 (10 min). One feature PR and one fix PR, each with the design choice, the alternative weighed, and the verification in the description. 124 tests cover the FHIR function.
  5. The project board and docs/BURNDOWN.md (5 min). Every change starts as an issue, is groomed with an estimate before it is Ready, and lands through a reviewed pull request. The definitions of Ready and Done are written down.

The repository is public: github.com/mvcprogrammer/mvcprogrammer.com, 278 commits since 2026-10-06, 162 pull requests. The grades below are mine; the links let you check them.

Three case studies

A problem, a decision, and where to see it. The bold text is the short version.

1. The FHIR explorer epic

Spec first, guard on the server, faults found by probing the live host. Visitors can create, change, and delete demo patients on a shared healthcare sandbox and can touch nothing else.

  • Decisions before code. Verbs, guard, budget, and idempotency were settled and written on epic #125 before the first slice.
  • Contract first. The OpenAPI document changed first; the function answered 501 until the handlers existed.
  • The guard holds no state. The seeded patient is read-only; every created patient carries the visitor's session token as a FHIR identifier; anything else answers 404, so nothing can be probed. PatientWriteService.cs
  • The sandbox enforces idempotency. A create is a FHIR conditional create keyed on the Idempotency-Key header; a retry returns the same patient with 200.
  • A library weighed and set aside. An eighty-line JSON Patch applier over five fields beat the general package; the reasoning is in PR #152.
  • Three edge faults, one afternoon, each with its cause written down. Cloned CloudFront behaviors allowed only the read methods; a signed request to a Lambda function URL needs the body's SHA-256 in a header; the single-page-app's 403-to-index mapping swallowed the API's own 403. All three are now runbook rules. PR #159

2. The four-editions mirror rule

One content change, four stacks, one commit. The same site ships in vanilla JavaScript, Blazor WebAssembly, Angular, and React from one bucket behind four distributions.

  • The rule is written down. A content, markup, or behavior change goes to all four editions in the same commit; each edition's colophon describes its own stack.
  • The rule under load. The explorer left all four editions in one change, 119 files removed and 48 changed, and the four test suites stayed green. PR #148
  • The payoff. The explorer itself was then built once, as its own Angular app at fhir.mvcprogrammer.com, rather than four times.

3. The engineering process

Issue before code, groomed before Ready, reviewed before merge, standard enforced by the build.

  • Every change starts as an issue on the public board and lands through a pull request that CI must pass.
  • Ready means groomed. Scope, acceptance criteria, priority, size, a Fibonacci estimate, and a sprint decision; the definitions of Ready and Done are in docs/BURNDOWN.md.
  • The build enforces the standard. The root .editorconfig names the rule behind each setting, violations fail dotnet build, and dotnet format runs on every PR.
  • AI assistants work under the same rules. Search public solutions before designing from scratch, compare two approaches, state the choice; the JSON Patch decision above came out of that rule.

Why this matters for revenue cycle work

FHIR R4 is how clinical data leaves certified EHRs, and the revenue cycle is a chain of data handoffs where bad inputs become denials.

  • Real R4, not a mock. The function parses live bundles from a public HAPI server with the Firely SDK, follows paging links, and maps only the US Core fields the page needs. Patient, Condition, Encounter, and Observation are the same resources that feed registration, coding, and charge capture.
  • The trace is an observability habit. Every upstream call is reported with its status, timing, and page count, so a silent EHR or payer failure has nowhere to hide. Application Insights and KQL are the Azure home for the same instinct.
  • The PHI boundary is designed in. Synthetic data only, nothing stored, request metadata the only thing logged, a guard that keeps one visitor from another's records, and a strict CSP in front of it all.
  • Where it would go next. Coverage and ExplanationOfBenefit views for the financial side, then a billing-readiness check: missing coverage, an encounter without a diagnosis, mismatched demographics. A small version of a pre-bill review.
